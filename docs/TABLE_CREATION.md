# Creating a table: ask for the schema first

Binding for every Claude session. It works together with `docs/CORE_RULES.md`.

## The rule
Before you write any `CREATE TABLE` (in SQL, in a migration file, or through the Neon connector), **ask the person which schema the table goes in.** Never pick one yourself, and never fall back to `public`.

Ask it in one plain question, with these three choices (admin, 26 Nov 2026, IT-0042: `telematics` removed; no prototype schemas):

| Choice | Use it for | Schema name |
|---|---|---|
| **Core** | Top-level tables: product tree, features, companies, users, branches, assets, asset groups, devices, SIM cards, device models, networks, data points, dealers, prices, quotes, subscriptions. | `core` |
| **GPS** | Detail and setup tables: asset details (vehicle, person, bin, generator, room…), personal details, certificates, alert setup, geofences, tickets. | `gps` |
| **Telemetry** | Big tables only: positions, events, alerts, readings, live states (one per solution), summaries, activity logs. Large and time-based. | `telemetry` |

Example question:
> Which schema should the table `vehicle_trips` go in? **Core** (top-level records), **GPS** (details and setup) or **Telemetry** (big device data)?

If the person already named the schema in their request, don't ask again.

## After the answer
- **Core**: allowed only on the developer's own branch `iotfy_<name>` (CORE_RULES rule 2). Tell the person in one line that it reaches `main` only through a core change request. Migration file goes in `db/migrations/core/`.
- **Telemetry**: same branch rule as core. Create the schema with `CREATE SCHEMA IF NOT EXISTS telemetry;` if it doesn't exist yet. Migration file goes in `db/migrations/telemetry/`.
- **GPS**: same branch rule as core; migration file in `db/migrations/core/`.
- In any schema: a table with a number id (`bigint GENERATED BY DEFAULT AS IDENTITY`) gets new ids in the app with `useNextIds`. Never make a second table with the same name in another schema (the apps find tables by name).
- **Neither fits?** Don't invent a new schema or a `proto_<name>` one. Say so in one line and ask the person (only the core owner can add a schema).

## Every time
- Always write the schema in the table name: `telemetry.vehicle_positions`, never just `vehicle_positions`.
- Every change is a numbered, re-runnable file (`CREATE SCHEMA IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`). CORE_RULES rule 7.
- Tables and columns in `snake_case`, `text` primary keys, foreign keys to `core` rows instead of copies (CORE_RULES rules 4 and 8).
- Demo data only.
